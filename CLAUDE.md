# Aerostorm Racing Website — Project Brief

Student-led F1-in-Schools/STEM racing team site. Static HTML pages, Tailwind CSS via CDN, no build step. Originally scaffolded through a no-code AI site builder (see `/_sdk/element_sdk.js`, `/_sdk/data_sdk.js` refs and Cloudflare snippet in HTML `<head>`/footer) — the live GitHub connection lives on that platform's side, not in this local folder, so treat `git remote` as needing to be (re)established, not assumed.

- Colors: base `#000000`/`#0a0a0a`/`#111111`, card surface `#1e1e1e`, borders `#2c2c2c`/`#1e1e1e`, body text `#e8e8e8`, muted grays `#636363`→`#bababa`, signature accent (champagne/gold) `#e0d2b3` with secondary shade `#d0bd92`. ## File map
- `index.html` (formerly `HomePage.html` — renamed so GitHub Pages serves it at the site root), `Engineering.html`, `Sponsorship.html`, `Updates.html`, `Contact.html`, `JoinTheGrid.html`, `PitWall.html` — content pages. Nav link ribbon and footer are now data-driven (see `site-chrome.js` below) rather than fully hand-copied, though the `<nav>`/`<footer>` HTML skeleton itself is still repeated per page. **`Gallery.html` no longer exists** (removed this session — see the `PitWall.html` entry below).
- `Contact.html` — split out of `index.html`'s old `#contact` anchor section into its own page (user: "Lets make Contact us a seperate page"). Renders email/phones from `homepage-content.json`'s `contact` field via `homepage-content.js` (loaded here too, not just on `index.html` — its other render functions no-op harmlessly since their container IDs don't exist on this page). The admin Homepage tab's Contact sub-section now writes data that shows up here, not on the homepage.
- `PitWall.html` / `JoinTheGrid.html` — live shared photo-gallery display + camera capture kiosk. **Now genuinely backed by `server.py`** — previously synced photos via `localStorage` only (per-browser, not actually cross-device despite the README claiming so); replaced with real endpoints (`GET`/`POST /api/wall-photos`, `POST /api/wall-photos/clear`) backed by a `wall_photos` SQLite table + `Images/wall/` (gitignored — these are live photos of event attendees, cleared between events, not permanent site content). Both routes are public/unauthenticated, matching the kiosk's original no-login design. **`PitWall.html` got the full standard nav ribbon** (previously just a logo + standalone "Join Grid" button, no link list) — the standalone button was removed since "Join Grid" is now a normal ribbon entry; `JoinTheGrid.html` also had its Contact-link exclusion removed, so both pages match every other page's nav exactly. **`PitWall.html` also absorbed the old Gallery page** (user: "I want gallery to connect to PitWall... get rid of the gallery Page, keep only PitWall") — below the live wall-photos grid there's now a second section rendering `gallery.json`'s curated images (same render logic `Gallery.html` used to have, now inline in `PitWall.html`'s own script block), with its own editable eyebrow/heading (`pw-gallery-eyebrow`/`pw-gallery-heading`, sourced from `pages-content.json`'s new `pitwall` key). The underlying `gallery.json` + admin **Gallery** tab (upload/caption/remove) are unchanged — only where the curated photos are *displayed* moved.
- `server.py` — the **single** backend (Python stdlib `http.server`, zero deps). Serves the whole site as static files (it's a `SimpleHTTPRequestHandler` subclass — run it locally to test anything that does a `fetch()`, since `file://` pages can't fetch local JSON), hosts the admin portal API under `/api/admin/*` (auth, content read/write, image upload, contact-submission management — see `admin_backend.py`), and two **public, unauthenticated** route groups: `POST /api/contact-submit` (Sponsorship form, replaces Formspree) and `GET/POST /api/wall-photos` + `POST /api/wall-photos/clear` (Pit Wall / Join the Grid). If this site is ever deployed with a public-facing backend, none of these routes have rate limiting — add some first. Run `python server.py --create-admin` once to set the admin login.
- `admin_backend.py` — SQLite-backed auth/sessions/audit-log/content-write/image-upload/contact-submission/wall-photo logic, imported by `server.py`. `admin.db` (gitignored, created on first run) holds one admin user (scrypt-hashed password), sessions, audit log, `contact_submissions`, and `wall_photos`. `python admin_backend.py --create-admin` (or `python server.py --create-admin`) prompts for email/password via `getpass` — **run this from a real Windows terminal (PowerShell/cmd), not Git Bash** — `getpass` reads the console device directly on Windows and piped/MinTTY stdin doesn't reach it. Running it again overwrites the one admin row, so it doubles as the "reset my password" path. Image uploads (Gallery tab) land in `Images/gallery/`, validated by extension allow-list and an 8MB cap; wall photo captures land in `Images/wall/` (same size cap, always `.jpg`, gitignored).
- `admin.html` / `admin.js` — the admin dashboard (local-only for now, not deployed publicly). Sidebar: Site Settings, Homepage, a **Pages dropdown** (see below), Menu, Updates, Sponsors, Gallery, Contact Data, Audit Log. Every content tab edits a real file (or, for Contact Data, the local SQLite table) and round-trips to the live pages; Audit Log is read-only. Row/card templates for list-editors (team members, menu items, sponsors, etc.) use explicit `grid-cols-[...]` templates with the remove button in its own column — don't go back to cramming an input + button into one flexed cell, that's what caused the tablet-width overflow bug fixed a previous session. **Every list-editor has a static column-header row above it** (e.g. above `#menu-list`, `#hp-team-list`, `#hp-phones-list`) labeling what each input column is for — user asked for this explicitly ("I want labels in admin so people understand what each input box does") since placeholder text disappears once a field has a real value typed into it. Keep this pattern (header row hardcoded in `admin.html`, hidden below `sm` since the row templates themselves reflow to fewer columns on mobile) when adding any new list-editor.
  - **Pages dropdown**: `#pages-toggle-btn` toggles `#pages-subtab-list` (`.hidden` class, no animation) revealing 5 sub-tabs — Engineering, Sponsorship, Updates, Pit Wall, Contact — each its own `.admin-tab-btn.admin-subtab-btn` with `data-tab="page-<name>"`, routing to `#panel-page-<name>` via the same generic tab-click handler (which now early-returns for the toggle button itself, since it has no `data-tab`). All 5 panels write to the SAME `pages-content.json` file, so each has its own `.save-pages-btn`/`.pages-saved-msg` pair (matched by class + `nextElementSibling`, not by unique id — there are 5 of each) all calling the one shared `savePagesContent(msgEl)` function in `admin.js`, which reads every `pg-*` field across all 5 panels regardless of which is visible (hidden panels keep their DOM/values, they're just CSS-hidden) and PUTs the whole object at once. If you add a 6th page here, follow this pattern: new sub-tab button + new `#panel-page-x` + fields reusing existing `pg-*` id conventions + its own save button/message pair — don't try to give it a unique top-level save function.
